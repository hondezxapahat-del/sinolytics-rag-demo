# Sinolytics RAG Demo — PRD v1.1

## Background

v1.0 是一个面向中国科技政策/产业简报的 RAG 问答 Demo：能够回答基于内部知识库（Sinolytics 出口管制白皮书、NEV 价格战两个主题的语料）的问题、生成一个 NEV 价格趋势图表、并在需要时查询网络获取实时信息，同时支持多轮对话上下文。项目最初作为 Sinolytics "Working Student – Data and AI Application" 岗位的技术验证作品完成，目标是展示一套具备生产雏形的检索问答能力、工具调用能力，以及轻量数据可视化能力。

这些构成了 v1.1 要在此基础上迭代的起点。

## Problem Statement

本产品当前面临的核心风险，是"什么样的回答才算好"这一标准尚未清晰界定，而这直接决定了产品是否有存在的理由。

如果直接套用通用大模型（如 ChatGPT）"面向全网、综合全面"的回答标准来衡量，本产品目前达不到——但这套标准本身可能就用错了：本产品理论上的核心价值，应该来自"公司内部专有行业报告的深度分析"与"外部实时信息"两者的融合与来源区分，而不是单纯在"全网综合能力"上跟通用大模型正面竞争。只要这个定位没有被明确下来，就无法判断当前与 ChatGPT 之间的体验差距究竟是需要解决的真问题，还是一次不恰当的对比——也就无法证明产品本身值得被使用。

这个定位风险，具体体现在以下几个尚未解决的缺口上：

- **内部检索与网络搜索"两张皮"**：内部文档检索结果和网络搜索结果目前分开展示，没有体现出两者融合后本该具备的增量价值——而这本应是相对通用大模型的真正差异化优势所在。
- **网络搜索结果质量偏弱**：接入的搜索 API 返回的新闻明显偏旧，削弱了"最新/趋势"类问题的可信度，也削弱了外部信息侧本该提供的时效性价值。
- **回答质量无法量化证明**：目前没有任何指标或数据支撑"这个系统靠谱"这一结论，无论是对内部文档问答，还是对趋势预测，都只能凭主观感受判断。
- **运行状态与成本不可见**：不清楚每次提问背后调用了几次模型、花了多少钱，出问题时也难以排查是检索环节、重排序环节还是生成环节出了问题。
- **对话历史不持久**：刷新页面或更换设备后，此前的对话记录就会丢失，体验更接近一次性 demo，而不是一个真正的产品。
- **面向外部输入缺乏防护**：提问框直接暴露给任何访问者，目前没有防止套话诱导、系统提示词泄露或诱导系统偏离既定行为准则的指令的机制。

## Goals & Non-Goals

### Goals（P0 — v1.1 必须完成，直接服务"护城河/产品定位"主线）

1. 产品定位为"内部 + 外部融合的垂直智能助手"，外部网络结果与内部行业报告分析明确标注来源、分开陈述，不混淆。
2. 新增"内部分析师风格"的趋势预测能力，且预测结果必须经过人工确认环节才能对外呈现。
3. 回答质量可被量化验证，而不是只能凭主观感受判断。
4. 运行状态与调用成本可见。
5. 对话历史持久化。
6. 具备针对外部恶意输入（套话诱导、系统提示词泄露、诱导系统偏离既定行为准则的指令）的防护。
7. 解决网络搜索结果明显偏旧的问题。

### Goals（P1 — 时间允许就做，来自 README 原有 Future Directions 清单）

8. 多模态文档解析（PDF、表格、扫描件）。
9. 更多图表主题/数据集，而不只是当前唯一的 NEV 价格战图表。
10. 与外部 BI 工具集成，让可视化产出接入更广泛的看板生态。
11. 多用户认证与限流。

### Non-Goals

1. 不做面向陌生公众用户的完整生产级系统——即便做了 P1 的认证/限流，也只是轻量防护，不追求企业级权限体系。
2. 不追求让 AI 的趋势预测全自动对外发布——人工确认环节是硬性要求，不存在"跳过人工审核"的模式。
3. 不扩充知识库语料覆盖的话题广度（不新增新的行业主题文档），v1.1 聚焦在现有语料上把质量做扎实。
4. 不做技术栈迁移或替换——v1.1 是在现有系统基础上的增量改进，不重新选型。
5. 不做多人协作/共享同一对话线程——持久化的对话历史仍是单用户视角的记忆，不是多人共同编辑。
6. 不承诺网络搜索时效性完全追平 ChatGPT 网页版——如果偏旧问题根源在数据源本身的限制，v1.1 只保证"在现有信息源下做到能做的最好"，不做无限背书。

## Requirements

### 产品定位 / 内外部来源区分

1. 针对同一话题，必须能同时呈现"内部行业报告怎么说"和"外部网络最新信息怎么说"，两者来源清晰标注、不混在一起呈现。
2. 当内部与外部信息对同一话题的判断不一致甚至冲突时，必须如实呈现这种分歧，不能自行调和成一个统一说法。

### 趋势预测 + 人工确认

3. 能基于内部分析师过往报告体现出的分析风格，针对某个话题生成简单趋势预测。
4. 趋势预测在展示给用户前，必须先经过明确的人工确认步骤；未经确认不能直接呈现给用户。
5. 界面上需清晰区分"经人工确认的预测"与"直接检索得到的答案"，避免用户把两者当作同一可信等级。

### 回答质量可量化验证

6. 具备一套可重复执行的评测方式，覆盖现有全部语料主题（中国 AI 大模型定价与市场、中国桌面 AI 办公 agent 市场、中国工业机器人装机、出口管制），而不是靠一次性人工判断。
7. 评测需能将本产品的回答与"不使用检索增强的通用大模型基线"做对比，用于证明本产品在这个垂直领域优于基线（具体评测方法留给后续技术文档设计）。
8. 需要有清晰、可解释的合格标准，而不只是一个抽象分数。

### 运行状态与成本可见（后台/开发者视角，不面向最终用户）

9. 开发者需要能看到每一次提问背后实际经过了哪些环节。
10. 开发者需要能看到每次提问产生的大致成本。
11. 出现异常或回答质量差时，开发者需要能追溯是检索、排序、生成还是预测确认哪个环节出的问题。

### 对话历史持久化

12. 用户换设备或刷新页面后，应能继续看到之前的对话内容。
13. 需要能回顾更早之前（不只是当前这次打开页面）问过的问题。

### 外部输入防护（轻量级）

14. 具备基本防护，能识别并拒绝明显的套取系统提示词/诱导系统偏离既定行为准则的指令类输入。
15. 即使遇到恶意输入，"外部结果必须标注来源""只依据检索资料回答"等核心行为准则不能被绕过。

### 网络搜索质量

16. 需要能呈现有实际时效性的网络信息，不能是明显过时的内容。
17. 若某次搜索确实没有找到足够新的信息，需如实告知"没有找到更新信息"，不能用旧信息冒充最新。

## Success Metrics

1. **来源区分**：随机抽取一批跨内外部信息的问题，人工检查回答，能清楚区分"内部报告观点"与"外部网络信息"，不出现来源混淆的案例。
2. **分歧呈现**：抽样检查中，遇到内部与外部结论不一致的情况时，系统如实呈现分歧，没有被自行调和成单一结论。
3. **预测经人工确认**：所有对外展示的趋势预测都能追溯到一次明确的人工确认记录，不存在未经确认就直接呈现的情况。
4. **预测可辨识**：不知情的读者（如面试官）能够仅从界面上准确分辨"这是经人工确认的预测"还是"这是直接检索得到的答案"。
5. **评测覆盖度**：已针对现有全部语料主题（中国 AI 大模型定价与市场、中国桌面 AI 办公 agent 市场、中国工业机器人装机、出口管制）建立评测集，并跑出本产品与"不检索的通用大模型基线"的对比结果。
6. **质量优于 baseline**：评测结果显示，在多数被评测的问题上，本产品回答质量不低于/优于 baseline（具体数字目标待第一轮评测跑出后回填，见 Open Questions）。
7. **运行状态可追溯**：任意一次异常/质量不佳的请求，开发者都能事后定位到具体是检索、排序、生成还是预测确认哪个环节出的问题。
8. **成本可见**：开发者能拿到任意时间区间内的调用成本数据，不存在"说不清楚花了多少钱"的情况。
9. **对话历史完整**：换设备或刷新页面后，此前的对话记录完整留存，没有丢失。
10. **输入防护有效**：用一组常见的套话/诱导系统偏离既定行为准则的指令测试用例验证，系统均未泄露系统提示词或被诱导违反核心行为准则。
11. **搜索时效性**：网络搜索结果附带日期，且没有找到新信息时会如实说明，不存在用明显过时内容冒充最新的情况。

## Out of Scope

- P1 目标（多模态解析、更多图表主题、BI 集成、多用户认证限流）如因时间原因未能在 v1.1 完成，顺延至 v1.2 及以后，不影响 v1.1 的验收，但也不能反过来拖慢 P0 的交付。
- 评测方法论的具体设计（如何构建评测集、是否需要消融实验等）不在本 PRD 讨论范围内，留给后续技术文档。
- 除本文档 Goals/Requirements 中明确列出的之外，任何未提出的能力，默认视为 v1.1 不做。

## Open Questions

1. "质量优于 baseline"的具体数字目标（如胜率、评分差距）尚未确定，待第一轮评测数据跑出后回填。
2. 网络搜索时效性问题目前只承诺"在现有信息源下做到能做的最好"，尚无可量化的时效性标准——是否需要在后续设定一个具体阈值？
3. P0 七项目标与 P1 四项目标之间，具体的开发顺序和时间安排尚未排期。
4. 人工确认环节由谁承担、通过什么方式触发确认，目前只明确了"需要有这一步"，具体承担者和流程留待后续讨论或技术文档中定义。
5. 后续技术文档（评测方法、消融实验设计、内外部融合展示的具体实现方案等）的撰写时间点尚未确定。
6. "baseline"目前在文档中所指对象不够明确——是"去掉检索能力的同一款模型"，还是字面意义上的 ChatGPT？这个需要先定下来，评测（Requirements #7）才有可比较的对象。
7. 人工确认环节与"现场演示"之间存在没解决的矛盾：Requirements #4 要求预测必须先经人工确认才能展示给用户，但 Success Metrics #4 又设想面试官能现场在界面上看到预测。如果是面试官临时提问，谁来做这次确认、什么时候做——这个流程还没有答案，直接关系到 Requirement #3（"针对某个话题生成简单趋势预测"）在现场演示场景下是否可行。
8. Requirements #2 要求"如实呈现"内外部结论的分歧，但"分歧"本身没有可操作的判断标准（多大的表述差异才算分歧？）；Success Metrics #2 目前只能靠人工抽样判断，缺少更明确的标准。
9. Success Metrics #10 提到的"套话/诱导系统偏离既定行为准则的指令测试用例"目前并不存在，需要先建立起来才能验证这条指标。
10. Requirements #1-2（内外部来源标注）和 Requirements #5（预测 vs 检索结果的可辨识度）是两套独立的标注需求，文档没说清楚它们如何共存：一个"融合了内部+外部信息的预测类回答"，界面上要同时体现几层标签？这是本产品核心卖点的呈现方式，值得在后续设计中优先厘清。
