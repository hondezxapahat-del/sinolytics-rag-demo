# Sinolytics RAG Demo — 技术方案 v1.2

> 本文档基于 [PRD_v1.2.md](PRD_v1.2.md) 撰写，描述账号登录、对话历史列表、年份幻觉修复、语言切换、以及回答具体性修复这五部分的技术设计。跟 v1.1 技术方案先设计再实现不同，这份文档是对已经写完并测试过的代码的如实记录。

## 1. 背景与目标

呼应 PRD v1.2：v1.1 已经把对话历史持久化做完（LangGraph `PostgresSaver` checkpointer，见 [TechSpec_v1.1.md](TechSpec_v1.1.md) §4.5），但没有账号概念，无法列出"我都问过什么"；同时实测中发现了一个可复现的年份幻觉问题；另外，产品面向的是一家"中国板块"咨询公司，使用者母语很可能是英文，需要一个能整体切换界面和回答语言的开关；实测还发现信息量大的文档（如出口管制白皮书）回答会读起来笼统，没用上文档里实际存在的具体信息。本文档记录这四部分的实际技术设计。

## 2. 现状分析（v1.1 完成后）

- 对话身份完全靠一个随机生成的 `session_id`，写在 URL 查询参数里；谁拿到这个链接就能读、能续写这段对话——TechSpec v1.1 §5 风险表已经点出过这条（"会话链接本质是隐性访问凭证"），当时没有解决方案，只能算已知风险。
- 没有"这个 `session_id` 属于谁"这个概念，也就没法列出"某个用户创建过的所有对话"。
- `/ask` 端点完全没有身份校验，任何人都能直接调用。
- 回答里偶尔会出现资料中不存在的具体年份（例如资料原文写"2026年"，回答却说"截至2024年"）——根源是现有提示词只禁止"补充资料之外的背景信息"，没有专门针对"编造年份/日期"这种看起来像措辞、实质是编造事实的情况做约束。
- 界面文字目前只有一种语言（写死在 HTML 里），没有切换机制；AI 回答用什么语言完全跟随用户提问用的语言，没有独立于提问语言之外的"当前界面语言"这个概念，也没有代码层面能覆盖它。
- `search_documents()` 里 `rerank()` 调用时 `top_n` 直接传的是 `match_count`（默认 3），这意味着不管命中多少个真正相关的片段，重排序阶段就已经把候选砍到只剩 3 个了；再往下 `MIN_CONTEXT_SCORE` 过滤是在这砍剩的 3 个里筛，起不到"按相关性动态决定数量"的作用。信息量大的文档（比如出口管制白皮书）实际上可能有 8-10 个片段清得过相关性门槛，但最终只有 3 个会被塞进答案生成的提示词——这就是回答读起来笼统的根源。

## 3. 总体架构设计

新增两张表：
- `users`：账号（用户名 + 哈希后的密码）。
- `conversation_threads`：`session_id` 归属 + 标题的轻量索引——不重复存实际对话内容（那部分仍然是 checkpointer 自己的表），只回答"这个 session_id 是谁的、标题是什么、最后更新时间"。

`/ask` 现在需要携带登录令牌；新增 `/auth/signup`、`/auth/login`、`/conversations`（列表）、`/conversations/{id}/messages`（读取某条历史）、`/conversations/{id}`（删除，`DELETE` 方法）几个端点。

```mermaid
flowchart TB
    subgraph Client[前端]
        LOGIN[login.html]
        SIDEBAR[ask.html 侧边栏]
    end

    subgraph API[api.py]
        AUTH[/auth/signup, /auth/login/]
        DEP[登录校验依赖<br/>解析 Authorization 头]
        ASK[/ask]
        CONV[/conversations 系列端点/]
    end

    subgraph Data[Supabase / Postgres]
        USERS[(users 表)]
        THREADS[(conversation_threads 表<br/>归属 + 标题索引)]
        CHK[(checkpoint 表<br/>实际对话内容，v1.1 已有)]
    end

    LOGIN -->|用户名+密码| AUTH
    AUTH --> USERS
    AUTH -->|签发令牌| LOGIN

    SIDEBAR -->|带令牌请求| DEP
    DEP -->|校验通过| CONV
    DEP -->|校验通过| ASK

    ASK -->|检查 session_id 归属| THREADS
    ASK -->|写入/更新归属记录| THREADS
    ASK -->|读写实际对话| CHK

    CONV -->|列表/删除| THREADS
    CONV -->|读取某条历史文字| CHK
```

语言切换不需要新表、也不新增端点——纯前端的界面文字翻译，加上 `/ask` 请求体里多带一个字段告诉后端"这次用哪种语言回答"，细节见 §4.4。

## 4. 详细设计

### 4.1 账号与登录

- 密码用 bcrypt 哈希后存储，数据库里不出现明文密码。
- 登录成功后签发一个有效期 30 天的令牌，前端存进浏览器本地存储，之后每次请求都带在请求头里。
- 没有账号找回/重置流程——密码丢了只能换个用户名重新注册。这是明确的 Non-Goal，跟"轻量登录"的定位一致，不是遗漏。

### 4.2 对话历史列表

- `conversation_threads` 只存"归属 + 标题"，标题取每个新对话第一句问题的前 60 个字符（超出部分截断）。
- 列表按最后更新时间倒序排列，最近聊过的排在最前面。
- **切换到某条历史对话时**，直接从 checkpointer 读取原始消息记录，还原成纯文字问答——由于结构化的来源引用、图表、预测标注这些数据从设计上就没有进入过 checkpoint 状态（TechSpec v1.1 §4.5 已经解释过原因），旧对话只能看到文字内容，看不到当时的完整展示效果。这是已知限制，PRD v1.2 里已经明确列进 Out of Scope，不是本次疏漏。
- 删除对话时，同时删掉索引表里的记录和 checkpointer 里的实际数据，不留孤儿数据。
- **一个关键的安全收益**：`/ask` 现在会检查"这个 `session_id` 是不是当前登录账号创建的"，不是就直接拒绝（返回 403）——顺带解决了第 2 节提到的、v1.1 遗留下来的"拿到链接就能读"这个风险，不需要额外方案。

### 4.3 回答诚实性修复（年份/日期）

三处同时修改，因为这三处是三条独立的、各自都可能生成用户看到的文字的路径，只改一处堵不住另外两处：

1. **内部检索的答案生成提示词**——明确加一条规则："只有资料原文出现过的年份才能提，资料没写明的不能自己补一个"。
2. **网络搜索工具返回给 Agent 的确认语提示**——这一步 Agent 本来就没有被告知具体结果的日期（只被告知"找到了 N 条结果"），所以明确告诉模型"你不知道这些结果的具体日期，你的确认语里不能提任何年份"。
3. **系统提示词的通用规则**——同样加了一条，管住最终合成回答这一层，不只是前两处工具相关的文字。

这类问题本质是模型的概率性行为，"改了提示词"不等于"100% 不会再发生"，只能说显著降低了概率——用之前复现过问题的问题反复测试多次，没有再出现编造的年份，但没有做过大规模统计意义上的验证，也不打算做（PRD Non-Goals 已经写明：这不是一次系统性的幻觉排查）。

### 4.4 语言切换

设计上刻意保持轻量：不引入任何前端框架或 i18n 库，只用一个纯前端的对照字典 + 一个请求参数就完成需求里的两块（界面文字、AI 回答语言）。

**界面文字（纯前端，不涉及后端）**

- 新增 `i18n.js`：一个 JS 对象，把每个需要翻译的短语按 key 存成 `{ en: "...", zh: "..." }` 的对照表。
- 需要翻译的 HTML 元素上打 `data-i18n="key名"` 标记；切换语言时遍历页面，把每个带标记的元素文字换成字典里对应语言的版本。
- `index.html`、`login.html`、`ask.html` 三个页面都接入这套机制；`review.html` 按 PRD 明确排除，不改动。
- 语言切换按钮放在每个页面右上角，跟登录状态按钮同一排——一个简单的文字按钮（"EN / 中"），点一下切换，不用下拉菜单。
- 选择存进浏览器 `localStorage`（对应 PRD 要求"记在设备上，换设备要重选"，本来就不写数据库）；没存过时默认英文。

**AI 回答语言（前端 + 后端）**

- `AskRequest` 新增 `language` 字段（`"en"` 或 `"zh"`），前端每次提问时按当前选中的语言带上。
- `run_agent()` 拿到这个参数后，往这次调用的系统提示词里追加一条指令："这次用 {language} 回答，不论用户提问用的是什么语言"——覆盖掉默认的"跟随提问语言"行为。
- 这条指令和已有的"不编造年份/日期"等规则是独立、不冲突的两类约束：一类管"写什么语言"，一类管"写的内容有没有依据"，同时生效。
- 这条指令不是绝对强制：提示词里会加一句"除非用户在这次提问里明确要求用另一种语言或双语回答，否则按上面的语言作答"——对应 PRD 需求第 14 条的例外情况。也就是说，中英混杂本身仍然是一种不希望出现的失败模式（见 §5 风险表），但"用户主动要求"是唯一被设计上明确允许的例外，不是同一件事。
- `web_search` 工具内部传给 Agent 的确认提示（比如"没搜到结果"那段内部说明文字）不需要跟着翻译——那段文字是说给模型看的内部指令，不是直接展示给用户的最终文字；用户实际看到的，是模型根据这段指令、按当前语言要求重新组织后的最终回答。

**系统固定提示语**

- `DAILY_LIMIT_MESSAGE`（每日额度用完）、`REFUSAL_MESSAGE`（拒绝可疑输入）这两处从单一英文字符串改成 `{en, zh}` 字典，按请求里的 `language` 字段选择对应语言返回。
- 登录/注册相关的报错提示（如"用户名或密码错误"）**不做**双语化——保持轻量的取舍，这两个请求发生在语言选择还没随请求传给后端的阶段，做起来需要额外改动，而实际触发频率低，性价比不高。

**不受影响的部分**

- 已保存的历史对话记录内容不做任何改动——旧记录是什么语言就还是什么语言，不会因为之后切换了界面语言被追溯翻译（PRD 已明确排除）。

### 4.5 回答具体性修复

**片段数量跟着相关性走，不写死**

- `hybrid_search` 的候选池大小（`CANDIDATE_COUNT`）从 5 调到 15，给后续筛选提供更多原始素材。
- `rerank()` 本身在一次批量 LLM 调用里就会给全部候选打分（`score_relevance_batch`），只是最后按 `top_n` 截断——所以把 `search_documents()` 调用 `rerank()` 时的 `top_n` 从 `match_count`（写死的一个小数）改成候选池的全部数量，不会多花一次打分调用的钱，只是不再提前把还没打分判断相关性的候选扔掉。
- 真正决定"塞进答案的有多少个"的，改成"清过 `MIN_CONTEXT_SCORE` 相关性门槛的全部片段，以 `match_count` 作为上限"——`match_count` 的角色从"重排序阶段的硬截断"变成"相关性过滤之后的安全上限"，默认值也从 3 调到 12。这样信息量大、真正相关片段多的话题能拿到明显更多素材，信息量小的话题也不会被硬凑。

**生成后自我核查**

- 新增 `_self_check_and_revise()`：把刚生成的回答草稿连同它依据的原始片段，一起交给模型做一次复查，明确检查两件事——① 草稿里是否用"多个/一些/显著"这类模糊词，代替了资料里其实写明的具体数字/日期/机构名；② 资料里有没有明显相关但草稿遗漏的内容。有问题就直接输出修正后的完整回答，没问题就原样返回草稿，不强行改写。
- 这一步只加在 `search_documents()` 的主回答生成之后，不覆盖 `_condense_web_findings`（网络搜索摘要）、`_draft_trend_prediction`（预测草稿）等其他生成路径——问题诊断出的根因只在"内部检索答案生成"这一条路径，没有证据表明其他路径存在同样问题，不做没有依据的连带修改。
- `search_web()` 内部检查、`_fallback_internal_analysis()`（预测待审核时的备选展示）都是直接调用 `search_documents()`，会自动带上这次修复，不需要单独改动。

**验证方式**

- 手动对比：拿"出口管制的机制和风险"这类信息量大的问题，分别用修复前后的代码跑一遍，确认修复后的回答明显更具体（点名了具体法规名称、具体表述），不是主观感觉。
- 量化验证：重新跑一遍 `evaluate.py`（PRD_v1.1 Requirement 7 已经建立的评测框架），确认修复后本产品相对 baseline 的胜率、各项 LLM-judge 分数没有因为这次改动变差——这正是 PRD_v1.1 从一开始就要求具备、但这次才第一次真正拿来验证一次具体修复效果的机制。

## 5. 风险与应对

| 风险 | 说明 | 应对 |
|---|---|---|
| 年份幻觉修复只是降低概率，不是根除 | 提示词层面的约束对 LLM 的概率性行为只能起到"大幅降低"的效果 | 已在 PRD Non-Goals 里明确这不是系统性排查；如果后续再复现，需要另外记录、另外处理，不能假设这条已经"解决" |
| 登录令牌长期有效（30 天）且没有主动失效机制 | 令牌一旦签发，在过期之前无法被单独吊销（比如换设备登录后，旧设备上的令牌依然有效） | 对于个人 demo 项目影响有限；如果以后要认真对外开放，需要补一个令牌黑名单或更短的有效期 + 刷新机制，目前不在范围内 |
| 历史列表标题只取问题前 60 字 | 如果第一句问题很长或者辨识度不高（比如"你好"），列表里的标题可能不够清晰 | 可接受的简化，不影响核心功能；真出现体验问题再考虑更智能的标题生成方式 |
| AI 回答语言指令和年份幻觉修复一样，是提示词层面的约束 | "用 XX 语言回答"这条指令同样是概率性的，不能保证 100% 遵守，理论上仍可能出现中英文混杂 | 同 4.3 节的取舍：反复测试没有复现，但不是数学意义上的保证；如果未来实测发现混杂，需要单独记录、单独处理 |
| 登录/注册报错提示不做双语化 | 这两个页面上，其余文字都会跟随语言切换，唯独报错提示还是英文，体验上不完全一致 | 已在本节和 PRD 里明确是刻意的轻量化取舍，不是遗漏；触发频率低（用户名密码错误等边缘情况），影响有限 |
| 片段数量上限提高后，响应时间和调用成本都会增加 | 更多片段意味着答案生成提示词更长；自我核查又多了一次 LLM 调用 | 已跟用户明确确认过这个取舍（响应速度/成本换回答质量）；如果未来发现成本过高，`match_count` 上限和是否启用自我核查都是可以单独调节的参数 |
| 这次修复没有在语料库规模远超现在的情况下验证过 | 现有语料库只有 4 个主题，候选池、片段上限这些参数是照着这个规模调的 | PRD Non-Goals 已明确排除；语料库真的大幅增长时，这些参数大概率需要重新评估，不能假设现在调好的值可以直接沿用 |

## 6. PRD Open Questions 解决方案

| # | PRD Open Question | 本文档的处理 |
|---|---|---|
| 1 | 登录状态多久算过期、过期后的体验怎么处理 | 已给一个默认值（30 天），但没有专门设计"过期后如何引导用户"的体验，目前只是被动跳转回登录页 |
| 2 | 历史对话只能看到纯文字，看不到当时的完整展示，要不要在未来解决 | 本文档不解决，PRD 已明确列为 Out of Scope；如果未来要做，核心决策是"要不要把更多结构化内容也持久化进历史记录"，这会改变 v1.1 §4.5 里"只存文字、不存大体积数据"的设计取舍，需要单独评估 |

## 7. 附录

**涉及改动/新增的文件**

- 新增：`auth.py`（密码哈希、令牌签发与校验）、`login.html`、`auth_and_threads.sql`（`users`/`conversation_threads` 建表）、`i18n.js`（中英对照字典 + 切换逻辑）。
- 改动：`api.py`（登录相关端点、`/conversations` 系列端点、`/ask` 增加身份校验和归属检查、`AskRequest` 新增 `language` 字段、`DAILY_LIMIT_MESSAGE`/`REFUSAL_MESSAGE` 双语化）、`ask.html`（侧边栏、登出按钮、请求携带令牌、接入 `i18n.js`、语言切换按钮）、`index.html` / `login.html`（右上角登录状态入口、接入 `i18n.js`、语言切换按钮）、`tools.py` / `agent.py`（年份/日期诚实性相关的提示词调整、按 `language` 参数追加回答语言指令、片段数量动态化、新增 `_self_check_and_revise()`）。

**仍需在实现阶段单独产出/明确的内容**

- 令牌过期后的具体用户体验（是否需要提示语、自动刷新等）。
- 年份幻觉修复的大规模统计验证（如果未来需要更强的信心，可以并入 4.3 节评测方法论的题库里，作为一类专门的测试用例）。
- `i18n.js` 里具体要覆盖哪些 key/文案，留到实现阶段边写边定，不在设计阶段穷举。
- 回答具体性修复的效果同样只做过抽样对比和一次完整评测跑分，没有做大规模统计验证——跟年份幻觉修复一样，是"显著改善"而不是"数学意义上的保证"。
